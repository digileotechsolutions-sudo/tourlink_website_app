# Payments deployment on cPanel

This application supports M-Pesa through the existing Daraja integration and hosted card checkout through Pesapal. Cash and bank transfers are recorded by administrators. Do not collect or store card numbers in TourLink.

## Before deploying

1. Take a database and application-files backup, and test the release on staging first.
2. Confirm the hosting account provides PHP 8.3 or newer, Composer, the PHP extensions required by `composer.json`, HTTPS, and a MySQL-compatible database.
3. Keep the Laravel project outside the public document root where possible, and set the domain document root to the project's `public` directory. Never expose `.env`, `vendor`, `storage`, or the application source through `public_html`.
4. Deploy the code and install production dependencies from the Laravel project directory:

   ```sh
   composer install --no-dev --prefer-dist --optimize-autoloader
   ```

5. Preserve the existing production `.env` and `APP_KEY`. Do not replace it with `.env.example`, do not generate a new key for an existing installation, and do not place provider credentials in source control.
6. Run `php artisan migrate --force` after backing up the database. This release adds payment method, receipt, manual receiver, payment metadata, and refund workflow fields.

## Configure providers

Administrators can enter or rotate credentials in **Admin → System settings → Payment gateway credentials**. Saved values are encrypted with Laravel's application key and never rendered back into the settings page. Credentials can also be provided through the server environment below; a saved admin setting takes precedence. Leave a field blank to keep its existing value; use its explicit remove checkbox to delete a saved override and fall back to the server environment. Restrict access to the admin account and maintain backups of the production `APP_KEY`; changing that key makes encrypted settings unreadable.

### M-Pesa

Alternatively, keep Daraja credentials and callback configuration in the server-side environment:

```dotenv
MPESA_ENVIRONMENT=production
MPESA_CONSUMER_KEY=
MPESA_CONSUMER_SECRET=
MPESA_SHORTCODE=
MPESA_PASSKEY=
MPESA_CALLBACK_URL=https://YOUR-DOMAIN/api/mpesa/callback
```

In the Daraja portal, point the STK callback to the application's existing `POST /api/mpesa/callback` endpoint over HTTPS. Use Daraja sandbox credentials and `MPESA_ENVIRONMENT=sandbox` only on staging.

### Pesapal

Set these environment values on the server; do not commit their real values:

```dotenv
PESAPAL_ENVIRONMENT=sandbox
PESAPAL_CONSUMER_KEY=
PESAPAL_CONSUMER_SECRET=
PESAPAL_IPN_ID=
```

1. Start with `PESAPAL_ENVIRONMENT=sandbox`.
2. Register the application's HTTPS notification endpoint, `https://YOUR-DOMAIN/api/pesapal/ipn`, in the Pesapal merchant portal using the currently supported Pesapal v3 IPN registration procedure. Select the GET notification method and save the IPN ID returned by Pesapal as `PESAPAL_IPN_ID`.
3. Configure sandbox consumer credentials. Do not use production credentials until Pesapal has approved the live merchant account and a complete sandbox payment/IPN test has passed.
4. The browser return URL is generated by the application for each payment. It only displays a pending/verification message; payment is considered successful only after server-side status verification from Pesapal.
5. Confirm the current Pesapal API v3 request/response fields, environment URLs, redirect domain, and notification behavior against Pesapal's current merchant documentation before enabling production. The gateway deliberately rejects redirect URLs outside the configured Pesapal host.

Never mark a card payment successful based only on a browser redirect or caller-supplied status. If an IPN is delayed, the payment remains processing until Pesapal reports its status.

## Activate the release

After code and environment changes:

```sh
php artisan config:clear
php artisan route:clear
php artisan view:clear
php artisan config:cache
php artisan route:cache
php artisan view:cache
```

If the hosting panel does not provide shell access, run the equivalent Artisan commands using its terminal/SSH facility or ask the hosting administrator. Do not make payment callbacks depend on a queue worker; current callback verification is handled synchronously.

## Smoke-test in staging

1. Sign in as a traveler, create a booking, and open **My bookings → Pay balance**.
2. Try a partial M-Pesa payment with Daraja sandbox values. Confirm that the balance only changes after the verified callback.
3. Try Pesapal sandbox checkout. Confirm a processing payment does not become paid from the browser return alone, then verify it after the IPN/status query.
4. As an administrator, record a cash payment and verify that a receipt is available. Record a bank transfer, confirm it remains pending, then verify it and confirm the balance changes.
5. Record a partial refund and verify that its status stays pending until the provider refund has actually been performed and an administrator marks it completed.
6. Check admin finance filters, cash/bank totals, traveler receipt authorization, HTTPS callbacks, and application logs. Do not use production money or credentials for a test.

## Production operations

- Configure and test HTTPS before registering provider callbacks.
- Restrict admin accounts and review manual payment/refund actions in the payment audit history.
- Back up the database before each migration. Test the migration and rollback on a copy; do not roll back production data without a recovery plan.
- Reconcile Pesapal, M-Pesa, cash, and bank statements against the admin Payments report regularly.
- Refund records in TourLink are a ledger/workflow only: the administrator must execute the refund with the provider or bank first, then mark it completed and record the external reference. This release does not call a provider refund API automatically.
- Receipts are downloadable HTML documents that can be printed or saved as PDF from the browser.
